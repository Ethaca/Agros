# Argos 웹앱, 처음 써 보기

Argos는 **코드를 바꿀 때 보안 문제를 함께 찾아주는 검토 도우미**예요. 로그인한 사람이 다른 사람의 자료를 볼 수 있는지, 비밀 열쇠가 코드에 들어갔는지 같은 문제를 살펴봐요.

예를 들어 학교 사물함을 생각해 보세요. 학생증이 있다고 다른 친구의 사물함까지 열 수 있으면 안 되겠죠? 앱에서도 “로그인했는가”와 “이 자료를 볼 권한이 있는가”를 각각 확인해야 해요. Argos는 이런 확인이 빠진 코드를 찾도록 도와줘요.

기본 리뷰는 **코드를 읽어서 문제를 찾는 방식**이에요. 운영자가 Docker 검사를 켜 둔 저장소라면 별도로 앱을 실행한 결과도 보여 줘요. 두 결과는 구분해서 읽어요.

## 1. 준비하기

필요한 것은 GitHub 계정, 검사할 저장소, 운영자가 알려 준 Argos 웹 주소예요. 저장소는 GitHub에서 프로젝트 파일을 보관하는 공간이에요.

저장소의 보호를 켜려면 **그 저장소의 관리자 권한**이 있어야 해요. 웹앱 사용자는 프로그램을 설치하거나 YAML 설정 파일을 만들 필요가 없어요.

현재 로컬 데모는 운영자의 컴퓨터에서 실행돼요. 운영자가 서버와 연결 프로그램을 꺼 두면 접속할 수 없어요. 주소가 바뀌면 새 주소를 받아야 해요.

## 2. GitHub로 로그인하기

1. 운영자가 알려 준 Argos 웹 주소를 열어요.
2. **GitHub 로 시작하기**를 눌러요.
3. GitHub가 보여 주는 접근 권한을 확인하고 승인해요.
4. Argos의 **레포지토리** 화면으로 돌아오면 로그인 성공이에요.

현재 버전은 GitHub **OAuth 로그인** 방식이에요. GitHub App을 따로 설치하는 과정은 없어요. Client ID나 Secret 입력을 요구받으면 운영자에게 알려 주세요. 사용자가 직접 앱 등록이나 서버 설정을 할 필요는 없어요.

승인하는 권한에는 비공개 코드 접근, PR 댓글과 검사 상태 게시, 저장소 알림 등록 등이 포함돼요. **로그인 승인의 접근 범위와 아래에서 보호를 켜는 저장소 목록은 달라요.** 현재 OAuth 권한은 저장소 하나에만 한정되지 않으므로, 데모는 테스트 계정과 저장소로 시작하면 좋아요.

## 3. 내 저장소의 보호 켜기

1. **내 레포** 목록에서 검사할 저장소를 찾아요.
2. 저장소 오른쪽의 **보호 스위치**를 켜요.
3. **보호 중 · PR 검사와 Threat Radar 감시**가 표시되는지 확인해요.

이제 GitHub가 “이 저장소에 수정 제안이 올라왔어요”라고 Argos에 알려 줘요. 이 자동 알림을 **Webhook**이라고 해요. 알림은 Argos가 등록하므로 직접 주소를 입력하지 않아도 돼요.

보호를 켰다고 예전에 열린 모든 PR을 바로 검사하는 것은 아니에요. 기존 PR은 5번의 **수동 검사**를 이용해요.

## 4. PR을 올리고 결과 보기

PR은 “이렇게 코드를 바꿨어요. 확인하고 합쳐 주세요”라는 **수정 제안서**예요.

1. GitHub에서 보호를 켠 저장소에 PR을 열어요. 처음에는 Draft가 아닌 일반 PR로 만들어 보세요.
2. Argos가 바뀐 코드를 검사해요.
3. PR의 대화 탭에서 **Argos 보안 리뷰** 댓글을 확인해요.
4. 문제가 표시된 코드 줄의 리뷰와 `argos/security` 검사 상태도 확인해요.
5. Argos 웹 화면의 **최근 검사**에서 해당 PR을 누르면 자세한 결과를 볼 수 있어요.

바꾼 코드를 같은 PR에 다시 올리면 새 커밋을 검사하고 요약 댓글을 갱신해요. 페이지에 예전 결과가 보이면 새로고침해 보세요.

지금 방식에서는 댓글이 **Argos에 로그인한 사용자 이름**으로 달려요. 별도의 봇 이름이 아니어도 정상이에요.

## 5. 이미 열린 PR 검사하기

보호를 켜기 전에 만든 PR이나 다시 확인하고 싶은 PR은 직접 검사할 수 있어요.

1. Argos의 **레포지토리** 화면에서 **수동 검사**를 찾아요.
2. 저장소를 선택해요.
3. **PR 번호**에 숫자를 넣어요. 주소가 `.../pull/12`라면 `12`예요.
4. **지금 검사**를 누른 뒤 **최근 검사**에서 결과를 확인해요.

연습 저장소 [gngsn/argos-realistic-app](https://github.com/gngsn/argos-realistic-app)에는 [테스트 PR #1](https://github.com/gngsn/argos-realistic-app/pull/1)이 있어요. 접근 권한이 있다면 해당 저장소의 보호를 켜고 PR 번호에 `1`을 넣어 보세요. 이 PR은 아래 두 문제를 일부러 넣은 예시이므로 **병합하지 마세요.**

- **BOLA:** 로그인은 했지만 다른 판매자의 자료까지 읽을 수 있는 코드.
- **SSRF:** 사용자가 넣은 주소로 서버가 검증 없이 요청하는 코드. 서버만 접근할 수 있는 내부 주소로도 요청할 수 있어 위험해요.

실제로 어떤 문제를 찾았는지는 생성된 검사 결과를 보고 확인해요.

## 6. 결과를 쉽게 읽기

먼저 위험도, 문제 위치, 설명, 권장 조치 순서로 읽어 보세요.

| 표시 | 어떻게 읽으면 되나요? |
|---|---|
| `critical` | 가장 급하게 확인해야 할 위험 후보예요. |
| `high` | 큰 피해로 이어질 수 있어 우선 확인해요. |
| `medium` | 어떤 조건에서 문제가 되는지 살펴봐요. |
| `low` / `info` | 상대적으로 낮은 위험 또는 참고 정보예요. |
| `none` | 이번 검사 범위에서 문제를 찾지 못했어요. |
| 검사 중 | 아직 결과를 만드는 중이에요. |
| 오류 | 검사를 끝내지 못했어요. 안전하다는 뜻은 아니에요. |

`app.mjs:48`은 `app.mjs` 파일의 48번째 줄이라는 뜻이에요. 위험도는 **확인 순서**를 정하는 표시이고, 실제 공격 성공을 증명하는 표시는 아니에요.

`argos/security`가 실패로 나오면 결과를 먼저 읽어 보세요. 기본 설정에서는 `high` 이상을 찾으면 실패로 표시해요. 이 표시만으로 GitHub의 병합 버튼이 반드시 막히는 것은 아니고, 저장소의 병합 규칙에도 연결돼 있어야 해요.

### 보안 영향 지도 읽기

상세 화면은 다음 세 가지를 연결해서 설명해요.

```text
무엇이 바뀌었나 → 누가 무엇을 할 수 있게 되나 → 어떤 피해가 생길 수 있나
```

예를 들어 “판매자 확인 조건 삭제 → 다른 판매자의 자료 조회 가능 → 자료 유출 가능”이에요.

- **코드 근거 포함:** 설명과 연결되는 코드 줄이 있어요. 실제 공격을 실행했다는 뜻은 아니에요.
- **가능성 · 확인 필요:** 다른 설정이나 호출 경로를 더 살펴봐야 해요.
- **실행 미검증:** 앱을 실행해서 확인한 결과는 아니에요.

**목적을 유지하는 안전한 대안**에서 고치는 방향을 보고, **직접 검증할 방법**에서 확인할 항목을 읽어 보세요. **이 이슈에서 배울 점**에는 쉬운 개념 설명과 다음 코드 검토에 쓸 질문이 있어요.

## 7. 문제를 고친 다음

### Docker 실제 실행 결과도 있다면

운영자가 연결한 저장소에는 PR의 **Docker runtime verification** 댓글과 `argos/sandbox` 상태가 추가돼요. 웹 상세 화면에서는 **Docker 실제 실행 검사**를 찾아보세요. 가짜 사용자로 실제 요청한 접근 결과표와 검사한 주소를 볼 수 있어요. 준비나 로그인이 실패하면 **검증 미완료**로 표시해요.

현재는 Express + SQLite 앱의 일부 읽기 API를 지원해요. SSRF 공격이나 모든 보안 문제를 실제로 시험하는 것은 아니에요. 검사하지 않은 범위도 보고서에서 확인해요.

1. 표시된 코드와 **권장 조치**를 읽어요.
2. 원래 필요한 기능을 유지하면서 권한 확인이나 입력 검증을 추가해요.
3. 정상 사용자는 계속 사용할 수 있고, 권한 없는 사용자는 거부되는지 테스트해요.
4. 고친 코드를 **같은 PR에 커밋하고 push**해요.
5. 새 커밋의 검사 결과와 갱신된 댓글을 확인해요.

이 웹앱의 일반 PR 리뷰는 수정 방향을 알려 줘요. 코드를 자동으로 고치거나 실제 공격으로 재검증해 주는 기능으로 읽으면 안 돼요. 문제가 없다고 나와도 검사하지 않은 코드와 다른 공격까지 안전하다고 보장하는 것은 아니에요.

## 8. Threat Radar는 뭔가요?

PR 검사가 “내가 방금 바꾼 코드”를 본다면, **Threat Radar**는 “내 프로젝트가 쓰는 부품에 새 보안 소식이 있는가”를 살펴봐요. 화면 메뉴에서 열 수 있어요.

예를 들어 내가 쓰는 Node.js나 라이브러리에 취약점 소식이 나오면, 저장소의 버전 정보와 비교해 알려 줘요.

| 단계 | 쉬운 뜻 | 할 수 있는 일 |
|---|---|---|
| L1 소문 | 관련 제보가 나왔어요. | 내용을 살펴봐요. |
| L2 교차 확인 | 여러 출처 또는 믿을 만한 출처에서 확인됐어요. | GitHub Issue로 대응할 일을 남길 수 있어요. |
| L3 공식 | 공식 보안 권고가 나왔어요. | 지원하는 변경에 한해 버전업 PR 초안을 만들 수 있어요. |
| L4 악용 중 | 공식 취약점이 실제 공격에 쓰인다는 근거가 있어요. | 우선순위를 높여 대응해요. |

**영향 가능**은 버전 정보가 부족해 확정하지 못했다는 뜻이에요. **지금 수집**으로 새 소식을 요청할 수 있지만, 목록이 비었다고 모든 취약점이 없다는 뜻은 아니에요. 로컬 데모에서는 정기 수집이 자동 실행되지 않으므로 필요할 때 이 버튼을 사용해요.

버전업 PR도 읽고 테스트한 뒤 병합해요. 이 기능은 일반 PR의 보안 문제를 자동 수정하는 것과는 달라요.

## 9. 잘 안 될 때

| 이런 일이 있어요 | 이렇게 해 보세요. |
|---|---|
| 웹 주소가 안 열려요. | 운영자에게 데모 서버와 터널이 켜져 있는지, 주소가 바뀌었는지 물어봐요. |
| 로그인할 때 Client ID 오류가 나요. | 운영자에게 알려 주세요. 서버의 로그인 설정이 필요해요. |
| 내 저장소가 목록에 없어요. | 새로고침하고 저장소 관리자 권한을 확인해요. 조직 저장소라면 조직의 앱 승인 여부도 확인해요. |
| 보호를 켰는데 아무 검사도 없어요. | 기존 PR은 **수동 검사**로 실행해요. 새 PR은 Draft인지도 확인해요. |
| 새 커밋을 올려도 검사가 시작되지 않아요. | 수동 검사를 시도하고, 운영자에게 Webhook 연결 상태를 확인해 달라고 해요. |
| 검사 결과가 오류예요. | 상세 화면의 오류 내용을 운영자에게 알려 주세요. |
| 지적이 틀린 것 같아요. | 다른 위치의 권한 검사 등 실제 근거를 확인해요. 코드 분석도 틀릴 수 있어요. |

## 10. 사용을 멈추려면

저장소의 **보호 스위치**를 끄고 확인해요. 해당 저장소의 자동 검사 알림 연결을 해제해요. 로그아웃만으로 보호가 꺼지는 것은 아니에요.

GitHub 계정의 접근 승인까지 취소하려면 GitHub의 **Settings → Applications → Authorized OAuth Apps**에서 Argos에 해당하는 앱의 접근을 해제해요. 가능하면 먼저 저장소 보호를 끈 다음 진행해요.

## 모르는 말 찾아보기

| 말 | 쉬운 뜻 |
|---|---|
| 저장소 / 레포 | 프로젝트 파일을 모아 놓는 GitHub 공간이에요. |
| PR | 코드를 이렇게 바꾸겠다고 올리는 수정 제안서예요. |
| 커밋 | 코드 변경을 한 묶음으로 저장한 기록이에요. |
| push | 내 컴퓨터의 커밋을 GitHub에 올리는 일이에요. |
| merge / 병합 | PR의 변경을 기본 코드에 합치는 일이에요. |
| API | 앱끼리 자료를 주고받는 창구예요. |
| 인증 / 인가 | 각각 “누구인가”와 “이 일을 해도 되는가”를 확인하는 일이에요. |
| 정적 분석 | 앱을 실행하지 않고 코드를 읽어 검사하는 방식이에요. |

서버를 직접 설정하는 운영자는 [로컬 데모 설정](DEMO.md)과 [Docker 실행 안내](../../docs/LOCAL_SANDBOX.md)를, 명령어로 앱을 실행해 검사하려는 개발자는 [CLI 명세](../../docs/SPEC.md)를 읽어 주세요.
