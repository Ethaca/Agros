# Canary 구현 계획

기준: `DEV_PLAN.md` 1~4절·6~9절, 2026-10-24 현재 저장소. 이번 문서는 계획만 다루며 기능 구현은 포함하지 않는다.

## 1. 범위와 현재 상태

목표는 `발급 → 유출 사본 식별 → 모의 모델 질의 → 증빙 리포트`를 CLI로 재현하는 것이다. TRACE를 별도 하위 명령으로 추가한다.

- `src/canary/` 및 canary 전용 테스트·데모는 아직 없다.
- CLI는 `src/cli.ts`의 Commander 명령 트리다. argv 직접 분기 대신 `registerCanaryCommands(program)`으로 연결한다.
- 현재 검증 체계는 `pnpm run typecheck`, `pnpm test`다. 옛 문서의 `eval`, `eval:mutation`, `github-e2e` 스크립트는 현재 `package.json`에 없다.
- 기존 접근 제어 결과는 `matrix.json`, `findings.json`, `scan-meta.json`이다. 단일 `argos-scan.json`을 가정하지 않는다.
- `src/checks/secrets.ts`의 환경 비밀 카나리와 이번 데이터셋 추적 카나리는 목적·형식을 분리한다.

1차 완료 범위는 템플릿 기반 issue·scan·probe·report 및 결정적 mock 데모다. 2차는 stress 필수 공격, 3차는 LLM 생성과 비교 실험이다. 웹 UI, 실제 모델의 탐지력 검증, PDF·전송은 범위 밖이다.

## 2. 먼저 확정할 계약

### 입력·재현성

- 최초 지원 형식은 UTF-8 JSONL, 행 스키마는 `{ id: string, question: string, choices: string[], answer: string }`로 제한한다. 보기와 정답의 관계를 검증하고, 임의 스키마는 명확한 오류로 거부한다. 일반 스키마 지원은 후속 확장이다.
- 원본 행의 내용과 상대적 순서를 보존하면서 합성 문항을 삽입한다. 원본 파일은 수정하지 않는다.
- 데이터셋 ID 기본값은 입력 바이트의 SHA-256에서 파생한다. 명시 ID를 주어도 원본 SHA-256을 별도로 기록한다.
- `ARGOS_CANARY_KEY`는 32자리 이상 짝수 길이 hex를 검증한 후 바이트로 해석한다. 키를 파일·로그에 기록하지 않는다.
- 토큰, 위치, 템플릿 선택은 HMAC으로 결정한다. 메시지는 구분자 연결 대신 JSON tuple로 직렬화하고, `token`, `position`, `control` 등 용도별 namespace를 둔다.
- 토큰의 두 영문자와 hex 12자는 digest의 겹치지 않는 부분에서 파생한다. 영문자 매핑의 편향을 피하고 발급 집합의 충돌을 검사한다.
- 결정성은 **템플릿 모드의 사본 바이트**에 적용한다. 레지스트리의 실행 시각까지 동일하다고 주장하지 않는다. LLM 재호출의 결과 동일성은 보장하지 않으며, 발급된 사본과 생성 정보를 보관해 재사용한다.

### 레지스트리·결과 파일

- Zod로 버전이 있는 `Registry`, `ScanResult`, `ProbeResult`, `StressResult`, `LlmUsage`를 정의한다.
- Registry: dataset ID·원본 해시·key ID·도구 버전·생성 시각·수신자별 사본 파일명/해시·문항 ID/토큰/삽입 줄/문항 내 prefix·대조 항목·생성 모드/전송 범위.
- 대조 항목은 발급 문항과 같은 생성 분포를 사용하되 어떤 사본에도 삽입하지 않는다. issue 시 생성·저장하고 probe는 저장된 개수 이내에서 선택한다.
- 결과에는 데이터셋 ID와 읽은 레지스트리 파일의 SHA-256을 넣어 다른 발급 건의 결과가 리포트에 섞이는 것을 거부한다.
- 키는 issue 및 내부 발급을 하는 stress에 필요하다. scan·probe·report는 레지스트리만으로 실행하며, 키가 제공되면 key ID 불일치를 거부한다. 이는 모든 명령에 키를 요구하던 초안을 좁히는 결정이다.
- 수신자명은 제한된 문자 집합·길이를 적용하고 중복, 예약 파일명, 경로 이탈을 거부한다. 기존 출력 덮어쓰기는 기본 거부한다.
- 출력 디렉터리는 700, 레지스트리와 민감한 결과 파일은 600으로 생성한다. 임시 디렉터리에 산출물을 완성한 후 최종 위치로 옮겨 부분 발급을 피한다.
- 공개 요약·리포트는 토큰 ID와 일치 길이를 사용한다. 전체 토큰, prefix, 모델 원문 응답은 기본 로그·리포트에서 제외한다.

### 판정·종료 코드

- scan: `IDENTIFIED | MIXED_SOURCES | UNIDENTIFIED`. 한 토큰이 반복되어도 고유 토큰 1개로 집계한다.
- probe: `status: VALID | INVALID_CONTROLS | INCOMPLETE`와 `verdict: SUSPECTED | NO_EVIDENCE | null`을 분리한다. 대조 항목이 4자 이상 맞거나 필수 요청이 실패하면 유효한 최종 판정을 내리지 않는다.
- canary 명령의 종료 코드: 0 정상/증거 없음, 1 식별·혼합 출처·오염 의심, 2 입력·설정·통신 오류 또는 무효/미완료 probe. Commander 사용법 오류도 canary 범위에서 2로 맞춘다.
- 기존 최상위 명령들의 종료 코드는 그대로 유지한다.

## 3. 구현 순서와 완료 기준

| 단계 | 구현 | 주요 파일 | 완료 기준 |
|---|---|---|---|
| 1 | 계약·CLI 연결 | `src/canary/{types,cli,errors}.ts`, `src/cli.ts` | 하위 help, 옵션 검증, canary 오류 코드 2 |
| 2 | 결정적 발급 | `token.ts`, `registry.ts`, `generate.ts`, `issue.ts` | 3개 사본, 원본 보존, 수신자별 다른 문항/토큰, controls 미삽입, 권한·해시 검증 |
| 3 | 유출 식별 | `normalize.ts`, `scan.ts` | 전체/일부/변형 식별, 무관 입력 미식별, 혼합 출처 분리 |
| 4 | 모델 질의 | `stats.ts`, `model-client.ts`, `probe.ts`, mock fixture | memorize/clean/대조군 일치/통신 실패 시나리오 통과 |
| 5 | 리포트·데모 | `report.ts`, `demo/canary-demo.sh` | 단일 스크립트로 전체 재현, 해시 일치, 한계·mock 표시 |
| 6 | 견고성 측정 | `attacks.ts`, `stress.ts` | S1~S5·S7·S9 측정, 기대와 실측 분리 |
| 7 | 선택 LLM 생성 | `llm.ts`, `generate.ts` 확장 | 반출 범위·호출 제한·검증·폴백·사용량 기록 |

5시간 목표를 유지한다면 1~5단계를 우선 완료하고, 6~7단계는 별도 완료 기준으로 추적한다. 원래 일정은 2명 병렬 작업을 전제하므로 전체 범위를 단일 작업자의 5시간 완료로 약속하지 않는다.

### issue

템플릿은 토큰을 자연스러운 제품/모델 식별자로 사용하고, 선택지·정답까지 일관된 문항을 만든다. 수신자별 문항 ID와 줄기를 다르게 생성한다. 삽입 위치는 결정적으로 선택하고 최종 1-based 줄 번호를 저장한다. 발급 전에 원본·모든 생성 문항·controls 사이의 토큰 중복과 오삽입을 검사한다.

### scan

NFKC → 명시적인 제로폭 문자 제거 → 영숫자 유지 → 소문자화를 토큰과 입력 모두에 적용한다. 원문 위치를 추적할 수 있게 정규화 결과에 원문 offset 매핑을 유지한다. 줄/레코드 경계를 가로지르는 우연한 결합은 일치로 세지 않는다.

NFKC는 전각 영숫자 등을 처리하지만 키릴 문자 같은 모든 시각적 동형문자를 복원하지 않는다. 지원 변형과 미지원 변형을 테스트·리포트에 구분한다.

증거에는 원본 사본의 줄과 유출본에서 발견한 줄을 각각 기록한다. 일부 유출·재정렬로 줄이 달라지는 것은 정상이다. 문항 ID나 토큰 주변 문맥이 다르면 `CONTEXT_MISMATCH` 경고를 붙이되 토큰 일치 사실은 보존한다. 문맥 검사는 모함을 완전히 방어하지 못하며, 단일 출처 식별도 행위자의 유출 책임 확정을 뜻하지 않는다.

### probe와 mock

`ModelClient.complete(prefix): Promise<string>`을 주입 가능하게 만들고, HTTP 어댑터는 `POST /complete`로 연결한다. 모델에는 prefix만 보내며 토큰 정답·레지스트리는 보내지 않는다. URL 검증, timeout, 응답 크기·스키마 검증을 둔다.

시험 토큰은 정규화한 completion의 시작 부분과 비교한다. 수신자별 10자 이상 일치, controls 전체 4자 미만일 때만 `SUSPECTED`다. controls는 최소 1개 이상이며 기본 5개다.

문서 수식의 10자 일치 확률은 이상화된 귀무모형에서 `1/(26² × 16⁸) ≈ 3.44e-13`이다. 이를 실제 모델의 오염 확률이나 검증된 유의확률로 해석하지 않는다. 기존 초안의 수신자 내 Bonferroni 값과 전체 실행의 비교 개수/보정값을 함께 기록한다. 모델 출력 분포와 질의 선택이 가정을 만족하는지는 별도 검증 대상이다.

mock 서버는 registry의 prefix를 매칭하고 지정 수신자의 토큰만 회상한다. clean은 고정 시드로 가짜 completion을 만든다. 테스트는 recall=1로 안정적으로 검증하고, 시연은 seed 고정 recall=0.8을 사용한다. 결과에 `modelKind: mock | external`을 기록하며 외부 모델은 실제 학습 여부가 확인되었다고 표현하지 않는다.

### report

발급·scan·probe·stress 결과를 묶어 Markdown으로 쓴다. 사본이 있으면 저장 해시와 파일 바이트를 비교하고, 없으면 `검증 불가`로 표시한다. 레지스트리 해시는 파일 자체를 읽어 계산한다. SHA-256은 무결성 비교용이며 서명·유출 책임 증명은 아니다.

기존 접근 제어 결과 첨부는 `--argos-scan <dir>`로 현재 `loadScan()`을 재사용한다. canary 데이터셋과 같은 시스템을 시험했다는 연결 관계가 없으면 별도 대상의 결과라고 표시한다. 견고성 표를 연결하기 위해 `--stress <file>`을 추가한다.

항상 명시할 한계: 미식별/NO_EVIDENCE는 유출·학습 부재의 증거가 아님, mock 결과는 실제 모델 탐지력의 검증이 아님, 부분 유출·삭제·재작성·공모에 취약, 통계 가정 미검증, LLM 데이터 전송 범위.

### stress

issue와 scan의 동일한 코어 함수를 재사용한다. 독립적인 seed로 S1 원본, S2 10/25/50% 줄 표본, S3 카나리 줄 제외, S4 지원 문자 변형, S5 정규식 제거, S7 두 사본 공통 원본만 유지, S9 타 수신자 토큰 주입을 만든다.

단일 출처 정확 식별률·혼합 출처 탐지율·미식별률·오귀속률을 분리한다. S9는 `MIXED_SOURCES` 검출 여부로 평가한다. S2를 Bernoulli 줄 유지로 구현하면 `1-(1-f)^k`, 고정 개수 비복원 표본이면 `1-C(N-k,m)/C(N,m)`을 사용한다. 20회 실험만으로 좁은 오차 범위를 요구하지 않고 분자/분모와 불확실성을 기록한다. S6·S8은 미실행으로 표시하다가 LLM 단계에서 확장한다.

### 선택 LLM

먼저 템플릿 모드로 완주한다. `--generate template|llm`의 기본값은 template로 명시한다. llm 선택 시 `--llm-data schema`가 기본이며 none은 네트워크 호출 없이 템플릿으로 처리한다. samples는 명시 선택 시 최대 5개만 전송한다.

LLM은 토큰 없는 합성 문항을 생성하고 토큰은 로컬에서 삽입한다. 스키마·정답·길이·금지 메타 단어·원본과의 20자 이상 공통 부분을 검증한다. schema 요청에는 실제 문항/보기/정답/토큰을 넣지 않는다. 필드 이름과 길이 통계도 전송 데이터로 기록한다.

총 시도는 수신자당 최대 2회로 정해 문서의 재시도 횟수와 기본 총 호출 상한의 모순을 없앤다. 실패·상한·키 없음은 템플릿으로 폴백하고 이유를 기록한다. 모델명, 호출 수, 지연, 토큰 사용량, 반출 모드를 `llm-usage.json`에 저장한다. 오류 본문과 프롬프트 원문은 로그에 남기지 않는다. SDK·모델 선택은 이 단계에서 공식 문서를 확인해 고정한다.

## 4. 테스트와 데모

테스트는 `test/canary-*.test.ts`와 `test/fixtures/canary/`에 배치해 현재 `pnpm test` 및 tsconfig에 포함시킨다. 별도 `test:canary` 스크립트는 같은 테스트의 선택 실행 용도로 추가한다. mock 서버 코드도 타입 검사 대상 경로에 둔다.

- 발급: 결정성, 원본 보존, 수신자 분리, controls 미삽입, 키·입력 검증, 경로 이탈·중복명·기존 출력 거부, 파일 권한.
- 식별: 전체/카나리 포함 일부/카나리 없는 일부/무관 입력/반복 토큰/정규화/문맥 변경/혼합 출처.
- 질의: memorize·clean, 일치 길이 9/10 및 control 3/4 경계, 수신자 선택, 잘못된 응답·timeout·일부 실패, 전체 비교 수 보정.
- 리포트: 해시 재계산, 다른 발급 건의 결과 거부, 파일 부재 표시, 비밀 미출력, 필수 한계·전송 범위·mock 표기.
- LLM: 스텁으로 실제 요청 반출 범위 검사, 20자 겹침 폐기, 유효하지 않은 생성 결과, 호출 상한·폴백·사용량 기록. CI에서 유료 API 호출은 하지 않는다.
- 회귀: `pnpm run typecheck`, `pnpm run test:canary`, `pnpm test`. canary 테스트는 루트 test에 포함되므로 기존 workspace CI를 사용한다.

`demo/canary-demo.sh`는 가짜 데모 키, 40문항 fixture, 수신자 3곳으로 issue → 카나리가 포함된 일부 유출 → scan → mock probe → stress → report를 실행한다. 탐지 종료 코드 1을 예상 결과로 처리하고, 실제 오류 코드 2는 실패시킨다. 서버는 빈 포트를 배정받고 readiness 확인 후 사용하며 종료 trap으로 정리한다. 최종 Markdown과 JSON 산출물 위치를 출력한다.

완료는 1~5단계 완주 및 회귀 통과, stress 필수 공격 실측, LLM 단계 검증을 각각 구분해 기록한다. 실제 모델 탐지 성능이나 모든 유출의 추적 가능성을 완료 조건에 포함하지 않는다.
