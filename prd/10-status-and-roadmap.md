# 10. 현황과 로드맵

## 구현 현황
| 영역 | 담당 | 상태 |
|---|---|---|
| 설정·계약, runner(프로세스/컨테이너), seed, matrix, scan | B | ✅ |
| 점검 4종 + 정적 스캔, `fix`(열 제한·소유자 검사) | B | ✅ |
| 시나리오 테스트, 출력 예시, `scan-meta.json` | B | ✅ |

| `argos report`, `argos ci`, 수정 PR 생성 | B(report는 A 몫이었음) | ✅ |
| `argos init` (AI 설정 초안) | A | ⬜ |

### SPEC 10절 인수 기준
충족: 1(결함 1~5와 수동 재현 일치), 2(소유자 접근 유지·공개 라우트 오탐 0), 3(리포트 헤더 해시가 재계산 값과 일치), 5(기동·대조 실패는 ⚪/오류). 미충족: 4(`init`), 6(`init → scan → fix → report` 3분 재생). `scan → fix → report`는 `argos ci`로 한 명령에 동작한다.

## 다음 할 일
1. **비개발자용 PR 메시지·보고서 상단 요약**(템플릿 기반, `11-ci-flow.md`)
2. **GitHub Actions 워크플로 예시**(`examples/argos.yml`: 컨테이너 격리, `argos/fix-*` 브랜치 건너뛰기, 권한)
3. **`init` (PLUG)** — 저장소에서 시작 명령·포트·헬스·스키마·소유 컬럼·토큰을 파악해 설정 초안을 만든다. 순서: 정적 스캔(LLM 없음) → 선택 파일만 LLM 전송(`.env`·키 파일 제외, 비밀 마스킹, 전송 목록 기록) → Zod 검증, 실패 시 1회 재시도 후 템플릿 폴백 → 실제 기동·로그인 검증 → 소요 시간과 사용자가 채운 항목 수 출력. 설정 계약상 `fix.principal`, `params`, `isolation`도 초안에 채운다.
4. `init` 연결(B)과 시나리오 S0 추가. A가 `report`를 따로 만들었다면 계약(`out/` 세 파일)만 맞춰 교체.
5. 고객 코드 보호 강화: 컨테이너를 어떤 조건에서 기본값으로 할지, 컨테이너 안 의존성 설치 단계, `node`가 없는 이미지 지원.

## 위험과 열린 질문
| 항목 | 내용 |
|---|---|
| 인증 방식 | 지금은 Bearer 토큰/없음. 앱이 JWT·DB 사용자·쿠키로 인증하면 `init`이 시험용 사용자를 시드에 넣거나 시험용 서명 키를 주입하는 설계가 필요하다. AI가 토큰을 "만들 수" 있는 것은 앱이 토큰을 환경변수·시드에서 읽을 때뿐이다 |
| DB | SQLite만. Postgres 등은 LATER. `seed.rows`(고객 제공 시드)는 미지원, 조직당 한 행만 시드 |
| 범위 | 블랙박스라 설정에 없는 경로는 못 본다. 라우트 자동 발견은 LATER |
| 자동 수정 | Express 스타일 SQL만. 프레임워크별 규칙, LLM 제안은 미구현 |
| `secrets (b)` | 매트릭스 응답만 검색(오류 유도 요청 없음) |
| 마스킹 | 앞 6자(`ARGOS_`)가 모든 마커에서 같아 증거만으로 마커를 구분하기 어렵다. 리포트에서 필요하면 종류 표기 추가 |
| 컨테이너 | `node` 필요, Linux에서 동작하는 의존성 필요, 연결마다 `docker exec` |
| 순환 논리 | LLM이 시험 대상 코드에서 `expect`를 추정하면 버그를 규칙으로 학습한다. 근거를 코드 밖에서 찾고, AI가 만든 `expect`는 사람 확인 전까지 "미확인"으로 표시한다(`11-ci-flow.md`) |
| 경쟁 제품 | 차별점(공격 증명 + 증빙 문서 + 쉬운 세팅)은 미검증 가설 |
| LLM 전송 | `init`은 소스 일부를 LLM API로 보낸다. 전송 범위를 출력·기록하고 `--llm-data none`으로 끌 수 있어야 한다 |
